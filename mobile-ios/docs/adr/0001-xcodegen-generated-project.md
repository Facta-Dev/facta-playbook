# ADR 0001 — XcodeGen-generated project

- **Status**: Accepted
- **Date**: 2026
- **Scope**: the build structure of the native iOS template

## Context

An Xcode project is a directory of `.pbxproj` files: an old-style property
list full of UUIDs, build phases and file references. It is generated by
Xcode's UI, not by a person, and every developer's Xcode rewrites parts of it.
Two branches that add a file each produce a merge conflict in a file nobody
reads, resolved by picking one side and losing the other file. The problem is
structural, not a matter of discipline:

- the file is machine-generated, so hand-editing it is fragile;
- UUIDs are opaque, so a diff is unreadable;
- Xcode upgrades rewrite the object version, creating noise in every PR;
- a file added on disk is not in the target until someone opens Xcode and
  clicks.

The template needs the opposite property: **the project definition is a
reviewable text file, and the project is a build artifact.**

XcodeGen reads a YAML manifest and writes the `.xcodeproj`. The manifest
declares the targets, the local packages, the build settings and the
`Info.plist` keys. It is one file, it diffs line by line, and it is the same
on every machine.

## Decision

**`project.yml` is the source of truth; the `.xcodeproj` is generated and
git-ignored.**

The rules that make it hold:

- `project.yml` declares one application target and the six local packages
  under `packages:`.
- Build settings that matter — `SWIFT_VERSION: "6.0"`,
  `SWIFT_STRICT_CONCURRENCY: complete`, the deployment target, the bundle
  identifier, the generated `Info.plist` keys — live in the manifest, never in
  Xcode's UI.
- `.gitignore` ignores `*.xcodeproj/`, `DerivedData/`, `.build/` and
  `.swiftpm/`; `scripts/check-architecture.sh` fails when an `.xcodeproj` is
  tracked.
- `make generate` (or `xcodegen generate`) produces the project;
  `scripts/native-gates.sh` generates before it builds, so a stale project is
  impossible.
- The app target's sources are a directory (`Apps/<APP>/Sources`), so a new
  Swift file is in the target without a project edit.

## Alternatives considered

| Option | Why not |
| --- | --- |
| Commit the `.xcodeproj` | Merge conflicts in an unreadable file, Xcode-version churn in every diff, and file membership becomes a manual step. The manifest exists to remove exactly this. |
| Tuist | A Swift DSL instead of YAML, with its own runtime and cache. It solves the same problem with more machinery than a six-package template needs. XcodeGen's manifest is smaller and needs no Swift toolchain to evaluate. |
| A Swift Package with an executable target | SwiftPM cannot build an iOS `.app` bundle: no app target, no `Info.plist`, no code signing. The app target must be an Xcode target. |
| Bazel / Buck | Hermetic and fast at scale, at the cost of a build system the team must operate and a ruleset per platform. The template is one app; the complexity is not paid back. |
| Generate the project once and commit it | The same conflicts return on the next Xcode upgrade, and the generator is then an unused dependency with a stale output. |

## Consequences

- **The build definition is reviewable.** A settings change is a YAML diff,
  not a binary blob; a reviewer can see the deployment target move.
- **Every machine generates the same project.** The manifest is the only
  input; Xcode's UI is a viewer.
- **New files need no project edit.** The source directory is the target's
  input, so adding a file is adding a file.
- **XcodeGen is a toolchain requirement.** `scripts/native-gates.sh` checks
  for it and prints a visible `SKIP` when macOS, Xcode or XcodeGen is
  missing; a macOS developer installs it once (`brew install xcodegen`).
- **The generated project is disposable.** `make clean` removes it;
  regenerating is one command.
- **Some Xcode features still need a file.** Entitlements and the privacy
  manifest are real files referenced from the manifest; the project remains
  generated, the capability files do not.
